## 本次发现并修正的差异

### 1. 原先把早餐铺的层参数用于三个主题

三个主题实际都使用容量 **150 / 60 / 45 / 45**，但高度是 **14 / 18 / 20 / 22**，不是早餐铺的 14 / 18 / 21 / 24。

| 主题 | 候选物品 | 初选种类（底至顶） | LimitHeight |
|---|---:|---|---:|
| 乡村 | 22 | 22 / 10 / 8 / 7 | 21.5 |
| 小卖部 | 22 | 22 / 10 / 8 / 7 | 21.5 |
| 烧烤 | 21 | 21 / 10 / 8 / 7 | 21 |

旧主题库把资源目录内的普通物品直接当作候选池，缺少每主题四种 `Goose_*`，乡村还额外包含 3 种、烧烤包含 8 种不在基础第二关名单中的物品。现在为第二关建立独立 `SourceLevelCatalog`，严格按原表 `NameList` 顺序解析全部对象；不重排第一关/PVP 的原有类型 ID。缺少模型时导入明确失败，不以替身或缩小候选池掩盖。

原表 `OtherTypeWeight` 原先没有接入，三个主题都是空权重。现按 `NameList` 逐项绑定数量权重，例如乡村 Apple=2、Goose_Watermelon=0.4，烧烤 Goose_Potato=1、RoastChicken=0.8。类型初选仍等概率不放回；数量权重用于后续三件组预算，不是初选概率。

### 2. 组数预算不是“每种保底一组再最大余数”

`j38517` 约 1000–1165 行先累计已选类型权重，然后对前 n−1 项计算：

```
group[i] = RoundToEven(float32(totalGroups * weight[i] / selectedWeightSum))
group[last] = totalGroups - sum(group[0..last-1])
```

`j1107` 明确实现中点取偶数：2.5→2，3.5→4。最后项按原顺序接余量；源代码没有“每种至少一组”，也没有把负余量再改成 Hamilton 分配。本次新增 `GenerateSource` 按此执行，保留零值和有符号余量。例：5 组、2 种等权是 2/3；2 组、5 种等权是 0/0/0/0/2；3 组、5 种等权可得到 1/1/1/1/−1。这些是公式边界例，后两项不表示当前三个主题每局出现这种配置。

每种物品汇总所有入选层预算，单件抽层；候选层按“是否初选”加入，包含零/负预算的条目，不能把它们静默删除。候选层满则移除重抽，空池从底向上找第一个未满层。已无容量时原函数结束该类型分配。当前三个主题的 3,000 个种子均保持 300 件、各层容量及全局三倍数。

### 3. 频率调整不包含项目额外的非负修正

对照 `j83882 / j83885 / j83886` 恢复 float32 累计权重与频率转移。源代码只限制被选项调整后的值位于 0–1，然后按其他候选的初始权重比例转移；原移植额外限制了每个接收项不为负，还会在总权重趋零时重置，这些都会改变后续分布，已从第二关源路径移除。

旧 `Generate` 与其保护保留给第一关等原有项目路径；第二关使用独立 `GenerateSource`，不会把旧保护宣称为原版规则。

### 4. 显示高度的初始化和下降条件不相同

`LoopCreateObj / j65137` 约 1530–1565 行：

```
maxHeight = firstRow.LimitHeight
touchHeight = maxHeight - visibleMin * 0.25
```

出生描述的初始显现条件（约 2200 行）是 `y >= maxHeight - visibleMin * 1.5`，即乡村/小卖部 15.5、烧烤 15。随后优化检查使用既有动态深度公式 `touchHeight - Lerp(4,5,Clamp01((21-touchHeight)/21))`。原实现直接以最高出生物品 Y 初始化，导致首次显示门槛偏高，已修正。

`j5870 → j19885` 只在当前堆峰低于记录的 `maxHeight` 时记录新低、再调用 `j9878` 让 touchHeight 最多下降 0.5。堆峰静止时不继续每秒追赶同一个高度；原项目每次检查都下降 0.5，不符这条条件。峰值计算排除已入槽对象（`isStore`，offset18；不是按住选中字段offset19），本项目收取时已通过 Detach 移出列表；本次也恢复峰值以零为下界。

### 5. 旧显现增长结论（已由创建阶段与门闩复核替代）

`ObjectUnit.Init / j19263` 清 `_isFinishCreate`（offset92），`CreateUnitObj / j13230` 先 Init 再 SetVisible；单看这条调用链不会触发重显分支；但前置 `_growUpInCreate` 已开启，开局可见物品仍按独立创建循环从零增长。随后 `FinishCreate / j9693` 才把标志设为 true。原移植会让开局可见物体全部长大，已修正。

`SetVisible / j6602` 在渲染状态变为可见且 `_isFinishCreate=true` 时进入 `DelayToGrowScale / j19265`；后者只有在 `_changeObjScale=true` 才清该标志、0→1 用0.75秒 OutQuad，完成回调 `sub j80061` 再设为 true。普通包未发现该门闩开启，下面只描述休眠分支：

- 长大中途隐藏后再次显示：标志仍false，既有动画继续，不重新开始。
- 长大完成后，后来又隐藏再显示：标志true，可以再次长大。
- 不是“物品一生只长大一次”；此前报告对此过度简化，本轮以完整写入/回调链纠正。

1 游戏秒检查、实体支撑保留、显隐可逆继续沿用。普通显隐不改变实体尺度与完成标记，不执行 .75 秒重显动画。三消仍不会新增实例。

## 仍然明确不同/尚未完成证据闭环

- 随机源仍为 `System.Random` 和项目每日种子哈希。原版类型/层抽签调用 UnityEngine.Random；源创建描述还有 `List.Sort` 比较器路径（j1965→j38270），当前空间打乱仍为 Fisher–Yates。不能保证相同 seed 或逐件创建顺序对应原版。
- 当前三个主题固定使用包内基础关卡 Index 1/4/5。线上选择每日模板、热更 `NetHardName`、AB、特殊 WinType/WinCount、活动变体和第一关流程未据此自动改造。
- 存量位置抽样的区间权重、离散框、矩形 X/Z 和 XYZ 随机旋转与已保存函数吻合，但随机调用顺序、分帧实例化时序仍不保证一致。当前开局同步构建物体；原版 LoopCreateObj 是分帧协程。
- 模型大小滑杆仍是用户要求保留的扩展；非 1.00 值不是原资源尺寸。
- 撤回落点、辅助匹配隐藏物品、其他模式仍需各自证据，不由第二关分层算法替代。
- 12 种补充鹅的渲染/骨骼、碰撞和尺寸由本轮资源复核并行处理；生成器本身要求资源完整，不能凭生成器通过就宣称新资源视觉与物理一致。
