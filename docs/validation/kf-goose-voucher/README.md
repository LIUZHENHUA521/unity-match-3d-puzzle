# 3D 红包客服识别修复（2026-11-11）

问题：此前游戏只打开专用客服链接；共享客服服务将红包欢迎语和自动转人工限定为 crazyCombo。近期 3D 红包存在，但对应游戏用户没有 UnionID，无法从客服用户反查游戏账号。

修复：登录后预取服务端签发的一小时随机客服票据，微信官方 `kf/add_contact_way` 生成的带 `enc_scene` 链接拼接 `scene_param`；点击时同步打开微信客服。票据只含随机数，不传玩家 OpenID。服务端在微信校验回调/消息同步的 enter_session 中原子消费票据，并按 sourceAppid/sourceUserId/sourceOpenid 查询本游戏红包；重复回调幂等，票据不能跨客服用户重用。

客服识别上下文有效七天，仅用于查询凭证是否存在及转人工；不写支付身份、不修改红包所有权、不触发支付。其他游戏继续原有流程。没有可验证身份或有效凭证时保持中性欢迎语。

微信的 welcome_code 和主动回复窗口由平台决定。无法再发送欢迎语的既有会话会尝试一次普通确认；明确拒绝后在玩家下一条消息重试，超时结果不盲目重发。从微信聊天列表打开旧会话不会携带新的游戏票据，首次关联需要从新版游戏内进入。

验证：客服服务 64 项测试通过；游戏后端 69 项测试通过（含真实 HTTP 鉴权与忽略伪造 owner）；客服 JS 桥接 7 项测试通过。共享服务 TypeScript 构建通过。全量共享服务测试另有 10 个旧支付用例使用 10 月 28 日前的固定凭证日期，在当前日期过期；未改支付源码的隔离 HEAD 副本同样复现 10 失败。本次不改支付行为。

上线前配置 `goose_invite_kf_context` 为 ADMINONLY，config 文档保存官方返回的场景链接和固定客服账号。所有构建使用隔离源码快照，不包含工作区已有的头像、关卡检查、旧身份解析及支付策略未提交改动。真机微信回调仍需用户用新版复验。

官方接口实际返回 `/kfid/…?enc_scene=…`；同时兼容文档中的 `/kf/…?enc_scene=…`，两种带签名场景的入口均有测试。
