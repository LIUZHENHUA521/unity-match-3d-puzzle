# 3D 游戏通关红包接入设计

日期：2026-10-31。用户已确认：复用疯狂动物消兑换机制，暂不改变游戏难度，按进入本科/清北的入口固定档位，完成两关后发对应凭证。后续由用户另行区分难度。

## 范围

- 本科 bachelor：easyPass，2 元，现有客服直接兑换。
- 清北 elite：pass，10 元，先完成对应游戏圈发帖任务并审核，经现有任务付款链路核销。
- 凭证有效期 7 天；保留现有付款锁、查询原订单、核销规则。首关仅为热身，不单独发钱。
- 复用 redEnvelop、后台红包列表、客服会话、任务审核及 transferCash；不另建余额或第二套支付系统。不调整现有物品生成、布局或难度。
- 不追溯旧版客户端通关，不从历史 themeId/stage 猜测档位。

## 入口与资格

首页本科开局指定 bachelor；清北进入主题选择时保留 elite。普通收藏回玩不隐式获取现金资格，需显式选择对应挑战入口。档位绑定一次 run，第一关、第二关、同一关重试保持不变；切档位必须退出并重新开始。

在线开局新增 POST /rewards/runs，身份取现有登录 token，客户端仅提交 tier、themeId、requestId。服务端验证配置后签发 runId，保存 owner、tier、themeId、北京时间 rewardDate、ruleVersion、两关配置摘要、issuedAt、expiresAt 和状态。requestId 在账号内幂等，重传返回同一 run。资格有效 24 小时；日期额度归服务端签发日期，截止前第二关结算必须到达服务端。过期仍可保存普通闯关记录，但不发券。未联网或拿不到资格时可继续普通游玩，开始前明确显示“本局未取得红包资格”，不伪装为可领奖对局。

本科额度键：gameId + owner + rewardDate + bachelor，每天一张；清北额度键：gameId + owner + rewardDate + elite + themeId，同一每日主题一张。这是对旧本科每日限制、清北具体关卡限制的适配；不跨游戏共享次数。凭证删除、作废或退款不会自动释放额度。

两关记录同时携带 runId、rewardTier、ruleVersion。服务端验证 run 归属和有效期、档位不可变、第一关已成功再接受第二关奖励结算、计数与该版本配置匹配、单局序号与时序一致、库存道具消费凭据属于该账号且未退款。旧 /records 接口继续接受普通统计，不允许仅凭旧接口传 rewardTier 升级为奖励资格。离线结算仅在资格有效期内补传并通过校验后发券；重复请求结果一致。

基础计数和时序校验不等于服务端复演，也不证明客户端没有作弊。第一版不宣称完整防作弊；凭证记录 verificationLevel=basic，客服与任务审核展示原始通关记录及此标识，仍保留现有人工审核。异常或无法验证的结算不自动发有效凭证，返回可追踪的拒绝原因。

## 发券事务和数据

新增 goose_reward_runs（开局资格）、goose_reward_claims（额度占用），均 ADMINONLY。索引覆盖 owner+issuedAt、owner+tier+rewardDate；claims 使用资格键哈希作为 _id，保证并发唯一。

第二关有效结算时，在同一 CloudBase 事务中写终局、检查/占用 claims、写 redEnvelop、给 run 和 record 绑定 voucherId。网络失败通过相同 recordId/runId 重试，返回原券。使用事务可访问多个实际集合的存储适配器，不让既有 goose_invite_ 表名前缀误写共享集合。

凭证保持旧解析器支持的 red:<毫秒时间>:<字母数字随机串> 格式。内容包含：

- 兼容字段：_id、type、money、createTime、isDelete。
- 来源：gameId=goose3d、sourceAppid、sourceUserId（现有哈希 ID）、sourceOpenid（仅服务端）、runId、recordId、rewardTier、rewardDate、themeId、ruleVersion。
- 奖励：amountCents=200/1000、expiresAt、verificationLevel=basic；金额和有效期由服务端策略快照确定。
- 兑换身份：redemptionUserId、redemptionAppid、openid（经认证关联后填写的兑换身份）、identityLinkId。未关联时不填假的 openid，不可付款；游戏仍可按 sourceUserId 查看自己的凭证。

sourceAppid 与兑换 AppID 分开保存，不能拿小游戏 openid 直接作为其他应用的收款 openid。记录查询按源账号，旧付款链路仍使用已认证的兑换 openid。

## 登录与跨应用身份

3D 微信登录继续维持现有 hash(appid + ':' + openid) 用户 ID，以免破坏邀请/库存。微信 code 换取身份时额外在服务端保存 sourceAppid、sourceOpenid 和微信实际返回的 unionid，旧账号在下一次登录补齐；这些字段不返回客户端。

新增 game_identity_links，关联 sourceAppid/sourceUserId 与现有兑换 user 的 ID、appid、openid，记录关联证据和时间。优先使用服务端已有的同一 unionid，且必须核对所属开放平台与来源，无法证明一致时不得靠昵称、手机号或客户端传值合并。

无可用 unionid 时提供一次性双端确认绑定：玩家在已登录的现有兑换入口发起绑定请求；服务端生成随机绑定挑战（5 分钟有效，绑定目标兑换账号）；玩家在已登录的 3D 游戏输入该码，服务端向两端展示掩码账号并要求分别确认。两端均确认后事务性消费挑战并写映射。单边知道凭证编号或分享链接不能完成绑定。挑战限频，不记录明文认证 token，不允许已经绑定的来源账号被静默改绑。需新增的绑定入口可位于现有 user-h5-Platform，不另建网站。

映射生效后，按 sourceUserId 将尚未提交任务、未锁付款的凭证关联到固定兑换身份。已提交或付款中的凭证不得改收款人。仍由现有客服身份解析/任务登录确认当前兑换玩家，并核对映射；不把新游戏用户伪装成旧游戏的原始账号。

## 兑换与兼容

- 保留 type=easyPass/pass，金额与旧策略一致。来源缺失的旧券继续按旧规则；gameId=goose3d 的新券必须经过来源、金额快照和身份关联校验。
- 本科走现有客服兑换，清北在客服页面显示去游戏圈任务，不开放直接转账。transferCash 的最终入口也保持此限制。
- 清北任务明确绑定允许来源 gameId/sourceAppid，并保留投稿所属游戏圈的审核；旧任务默认只接旧游戏凭证，不因 type 相同自动接入 3D 凭证。在现有任务系统建立 3D 游戏圈活动配置，审核、付款及凭证占用共用原生命周期。
- 所有使用 voucherLifecycle 的独立云函数用现有同步脚本更新同一份逻辑，避免提交、审核、付款不同步。新增接口必须核验管理员/玩家身份，不能沿用客户端任传 openid 的调用方式。
- 付款前在事务中锁定 voucherId、兑换账号、金额、商户和 billNo；未知结果只查询原单，不另建单付款。共享的任务渠道与客服渠道互斥占券，成功后再核销。
- 3D 来源的金额不得由客户端或后台普通编辑变更；需要人工补偿时走明确的单独运营发券功能，不改已有付款上下文。

## 客户端与后台

Unity 结算弹窗显示资格校验/发券结果，可重试查询；新增“我的红包”列出待绑定、待兑换、审核中、付款处理中、已兑换、已过期状态，提供复制凭证和对应兑换引导。列表和凭证只按登录账号返回。主题第二关结果只有服务端确认 voucherId 后才显示“已获得红包凭证”。

后台沿用红包菜单：贯通 gameId/appid 筛选，新增来源游戏、档位、金额、关联通关、资格验证状态、身份关联状态与兑换状态；用户详情按来源分派，不能把哈希账号当成旧游戏 openid。闯关记录新增档位与凭证链接。保持既有菜单权限，不自动扩大普通角色付款权限。

## 发布顺序与验证

1. 先补身份关联、共享红包/任务/付款的来源兼容与测试，默认关闭新游戏发券开关。
2. 部署 goose-server 资格/发券模块与集合索引；部署相关共享 Node 服务、云函数、H5 绑定入口和管理后台。部署前核对线上函数、提交推送各仓库，通过本机 CloudBase MCP 发布并保留既有配置。
3. 构建客户端，验证本科/清北入口、切关、重试、离线资格提示、我的红包、账号绑定。当前用户未要求正式发布小游戏，不自行提审或发正式版；新版客户端发布与开关启用须在接入验证完成后明确交付。
4. 测试：开局幂等/越权/切档拒绝；第一关不发券；第二关要求同一资格的首关完成；两档额度隔离；并发发券唯一；过期和旧记录不补发；身份双端确认/过期/重放/跨账号拒绝；旧券回归；本科客服与清北任务渠道隔离；任务来源不匹配拒绝；支付未知/重试/成功核销。使用模拟付款覆盖所有支付路径，未经明确要求不向真实账号测试打款。
5. 线上用明确测试来源做查询和授权验证，清理自建测试数据；提供可追踪的部署版本、测试结果及尚待真机验证事项。

## 交付前需核对的现网配置

现有商户可用 AppID/收款授权、3D 来源游戏圈任务目标和发布状态、双端绑定入口可达性均以只读检查为准，不猜测配置、不修改既有商户。缺少配置时保留已完成代码并准确报告，不能把“接口已部署”当成“真实兑换已可用”。
