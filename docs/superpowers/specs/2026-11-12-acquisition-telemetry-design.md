# 分享与广告分渠道上报

用户已确认把上报中的分享、广告及复活分别记录。本次沿用每关结算与持久化补传队列，不引入独立事件集合。

## 数据口径

- 仅统计获取成功且效果实际生效的次数；未完成广告、失败分享、重复或过期回调不计数。分享是客户端返回判定，不代表微信确认送达；广告是成功获取奖励，不代表全部展示或点击。
- 新结算附带 `acquisitionVersion: 1`。每项 `toolUsage` 新增整数 `share`、`ad`，保留 `rewarded = share + ad` 兼容现有道具与红包校验。
- 新增 `reviveUsage.clear` 与 `reviveUsage.time`，分别保存 `free`、`share`、`ad`。每种复活每局最多一次，`timeReviveUsed` 与加时复活计数保持一致。每关准备、重试重置，结算时序列化后补传不再更改。
- 无标记的旧请求按原有规则规范化，保持历史重复请求幂等；不自动填充渠道零值。新请求严格验证字段完整、整数范围、合计与复活一致性。

## 展示与兼容

已有共享管理后台“3D 游戏 / 闯关记录”增加每条结算记录的分享、广告成功获取总数（道具+复活）以及详情分项。旧数据明确显示“未区分”，未结算显示“待结算”。旧的 `rewarded` 文案更正为“分享/广告未区分”，不冒充广告数。不新增菜单、权限或云函数接口；现有查询原样返回记录字段。

## 验证与发布

覆盖客户端实际成功、失败、重复回调、重试清零与 JSON 结算；服务端普通记录和红包路径的新旧兼容、非法计数拒绝、幂等补传；后台新旧/未结算展示与构建。优先服务端兼容接收，再发布客户端；后台按照用户长期约定部署。客户端新包到达玩家后才会开始收集新字段，历史记录无法可靠回填。

## 边界

独立实时事件流能覆盖未结算关卡，但会引入事件幂等与接口维护，本轮不扩展。缺第一关通关凭据的奖励问题另行处理，不借本次统计变更绕过校验。
