# 3D 每日关卡：日期、档位与玩家种子

用户已确认：第一关保持 15 个；第二关按日期分别配置本科与清北，层数、每层数量、类型数和高度、整局限时可编辑。首次本科 300 / 600 秒，清北 450 / 600 秒。每天每位玩家每档位种子固定，不同玩家不同。

## 配置与发布

共用管理后台 /goose-daily-levels；草稿和发布分离，复制前一天的生效配置，显示未来排期。1–10 层，每层 3–600 且为 3 的倍数，类型 1–min(23, 数量/3)，总数不超过 1200。层顶从 1.5 以上逐层递增，最多 30；限时 30–3600 秒。参数客户端、后台和服务端都校验。

`goose_daily_levels`（ADMINONLY）存放 draft-date-tier、published-date-tier、version-版本、schedule-tier。发布版本不可变，更新排期和发布文档同一事务，草稿 revision 乐观锁防覆盖。当天未发布时选择 <= 当天的最近发布；从未发布则使用已确认默认档位。

## 开局与稳定重试

`goose_daily_players`（ADMINONLY）按玩家、服务端北京时间日期、档位、生成算法版本唯一键保存首局配置快照和服务端随机种子。后续开局与重试均返回同一快照；当天改配置只影响尚未锁定的玩家。次日重新锁定配置和种子。

红包开局协议 levelProtocol=1，服务端在同一事务获取快照并写入 run，回传完整 level。无新协议的旧客户端新红包开局要求更新，已签发的旧局继续按原快照结算。测试账号通过 /levels/daily 获取相同每日配置但不参与红包。收藏普通回玩保持旧入口。红包总开关不因关卡配置上线而开启。

客户端采用 daily-v1 的局部 xorshift 随机流，不污染 Unity 全局随机状态，第一关和第二关独立派生随机流。每层完整三消组分配，每种选中类型至少一组；固定物品描述/初始位置生成，物理落位可能仍有细微差异。通关记录带日期、档位、版本、种子、算法版本。红包服务端校验这些标识以及快照中的总数和限时，不因后续发布更改旧局。
