# Pot replay reliability

Implements the four repair areas approved in conversation on 2026-11-16. Preserve the v2 replay protocol, current persistent identifiers, game outcomes, and 64 MiB JSON / 16 MiB upload safety limits.

- Persist per-record state (recording, queued, uploading, synced, failed), ownership, date/tier, failure reason and retry metadata. UI chooses cloud ready first, then actual local queue/failure state. A local win without a matching file must not claim an upload is pending. Persist diagnostics and retry reporting through an authenticated, bounded endpoint; reject cross-account records. Failures never interrupt game settlement.
- Keep 10 Hz sampling and all gameplay events; quantize positions/scales and normalized rotations, compare against last emitted state (not previous sampled state), and avoid irrelevant movement of invisible/removed items. Full checkpoints every 30 seconds retain every object for random access. Preserve visuals within quantified tolerance and verify long sessions stay under limits.
- Queue wins before other recordings, use per-record bounded exponential retry, preserve raw network errors, recover interrupted uploads across startup, and recover legacy complete rejected files only for safe retry. Terminal failure must be explicit. Cleanup failed recording groups after a retention window, only for the current owner and never delete valid queued recordings; keep enough metadata for failures. Isolate malformed files so one cannot block startup recovery or the upload queue.
- Audit existing online incoming files for missing wins. Only validate complete real files against the original game record using existing validation before any recovery; never relabel incomplete files as wins. Preserve source data. If no complete file exists, report that recovery is impossible from server data.

Verification: meaningful state/queue/restart regressions, legacy compatibility, 30-minute synthetic moving-board recording with budget and seek checks, backend diagnostic authorization/size bounds, and upload finalize regression. Clearly distinguish synthetic validation from real-device testing. No automatic client release or service deployment is requested by this repair task.

Concrete acceptance: encode position/scale to 0.001 units, quaternion components to 0.0001 (normalize for comparisons), target position/scale error <=0.002 units and angular error <=0.1 degree for emitted visible poses. Compare to last emitted pose to prevent accumulated sub-threshold drift. Test 330 objects for 18,001 samples (30 minutes at 10 Hz), including static jitter, 12 moving visible objects, visibility/removal transitions and periodic checkpoints; require JSON <64 MiB and gzip <16 MiB, and seek reconstruction within tolerance. This is a representative synthetic workload, not a claim for every possible full-board continuous-motion sequence.

Retry starts at 5 seconds and doubles to a 5-minute cap, with no terminal retry count for transport/auth/server failures. Permanent validation failures retain complete files quarantined; never automatically delete these or queued complete files. Cleanup applies only to explicitly failed, incomplete raw journals after 7 days, after persisting the reason; preserve metadata for 30 days. Legacy rejected complete files get one retry per repair-version marker; if rejected again, quarantine and show failure. Prune metadata only for terminal records without payload, never recoverable complete files. Server recovery audit may find no eligible incoming files and must report that accurately.

Implementation evidence found old invisible rigidbodies falling beyond coordinate limits. Server canonicalization accepts only finite out-of-range positions on fully invisible items, replacing position with last valid state; visible invalid transforms remain rejected. Newly recorded removed objects outside board bounds are suppressed before serialization. Old complete recordings that also contain visible invalid transforms are retained for manual investigation, not force-published as valid replays.
