# 回放缓存积压修复验证

本轮完成代码修复与本地验证，未部署服务端、未构建或上传新的微信版本。设计文档提交 7a293fb2；实现与验证改动保留在工作区。没有修改生产通关、回放或奖状数据。

## 改动

- PotReplayRetention 对当前账号已确认的非胜局录像设 32MiB / 3 局 / 2 天预算，并在总目录超过 64MiB 时回收可淘汰非胜局，为新局预留空间。以独立 retainedAt 计龄，重试不续期。胜局、元数据未知/冲突、其他账号和正在恢复/上传的记录受保护。清理原因留在账本，已删除的非胜局不再上传。128MiB 原硬门槛仍保留；当空间由受保护文件占满时，不保证新录制成功。
- 开新局/播放回放/短期内存保护使 gzip 与 journal 恢复暂停；空闲后从同一流的位置继续。账号切换取消，服务销毁显式 Dispose 嵌套队列，关闭流、释放保护、清理半成品、保留原文。进程退出仍需重新压缩，未实现跨进程压缩断点。
- 原 Reconcile 也跳过活动记录，防止新局在后台恢复中途删掉打开的 journal。已知胜局的部分恢复不再覆盖账本 win 结果。
- honors 新增兼容字段 replayState，基于匹配 owner/recordId/runId/stage/status 的诊断返回 pending/uploading/unavailable；已确认 ready 索引优先。客户端显示“回放待同步 / 回放同步中 / 本局未保存”，旧接口兼容；有本机最新状态时按账号补充判断。未保存提示不再承诺稍后重试能恢复。
- 录制开始即记录真实客户端与回放版本，避免录制失败诊断版本为空。

## 验证结果

1. 服务端 npm test：175 通过、0 失败，包括荣耀状态、索引优先级、旧记录与身份/对局错配、字段泄露回归。
2. 原生文件与上传桥接 Node 测试：5 通过、0 失败。
3. Unity run-reliability.py：缓存容量/局数/年龄、重试不延长保留、旧非胜局积压回收、胜局/未知/其他账号/活动文件保护、部分清理重试、压力中暂停恢复、切换账号与销毁取消等均通过。
4. Unity 真序列化长局：1800 秒、330 个对象、18001 个采样；JSON 42,194,777 字节，gzip 1,776,523 字节。已写入 gzip 后暂停 30 个迭代，文件大小保持不变；恢复后的解压内容与不中断压缩完全一致。原取消/崩溃残留/重试复用/精度验证继续通过。
5. 荣耀 HTTP + Unity 页面集成：三种无回放状态分别显示；未保存点击不发起下载；分页、奖状查看、重试、账号切换继续通过。检查了长屏截图，未保存文字正确显示。
6. 原首页回放 HTTP + Unity 集成：上传幂等确认、重试与持久化、首页刷新、账号隔离、下载取消、播放/退出全部通过。
7. 两个仓库 git diff --check 通过；Python 验证脚本编译通过。

测试发现并修正了两处测试条件：gzip 首次协程 yield 可能仍在内部缓冲区，续压验证改为确认有实际输出后再暂停；首页旧夹具会停用服务后直接调用上传，新增生命周期取消正确阻止该调用，夹具改为处置自动队列并启用显式调用的服务。

结果文件位于 docs/validation/pot-replay-cache-recovery/。Unity 验证使用带入当前完整 Assets/Packages/ProjectSettings 的隔离项目，未关闭或覆盖用户打开的编辑器工程。未连接手机真机，因此没有声称完成真机连续失败重开与通关验收。
